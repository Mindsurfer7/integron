# Human-in-the-loop: владелец участвует в процессе звонка

**Приоритет:** P1 обязателен для последующего P3/P4/P5. По умолчанию уведомление отправляется **Telegram Bot API**; WhatsApp — альтернативный канал после P7. Это уведомления от бота владельцу, а не сообщения внешним организациям.

## 1. Поводы спросить владельца

- Неизвестное предпочтение: выбрать вариант услуги/цвет/срок/условие.
- Организация просит явное согласие: запись, оплата, раскрытие личных данных.
- Непредвиденное предложение, выходящее за рамки task brief.
- Критическая неоднозначность распознавания речи или противоречивые ответы.
- План ограничен бюджетом/политикой, а новый шаг требует расширения разрешения.

Не спрашивать владельца то, что агент может уточнить у организации сам; не выводить на связь владельца по каждому тривиальному вопросу. Approval — отдельный тип уведомления, а не обычное уточнение.

## 2. Пример сообщения владельцу

```text
🤖 Integron · задача #T-104
📞 Сейчас разговариваю с магазином B [WhatsApp]

Они предлагают 2 модели в наличии. Какую цену/модель подтвердить?
[A — 3 200 ฿] [B — 3 900 ฿]
[Не подтверждать; уточнить позднее]

Вопрос #Q-918 · ответ желателен сейчас
```

Не отправлять в Telegram конфиденциальное содержание разговора без настройки владельца. Можно заменить названием «организация B» и кратким безопасным резюме.

## 3. Протокол

```ts
type ClarificationRequest = {
  id: string;              // unpredictable opaque ID
  taskId: string;
  conversationId: string;
  callId?: string;         // null for async text
  ownerUserId: string;
  reason: 'preference'|'missing_information'|'approval'|'conflict';
  question: string;
  options?: { id: string; label: string }[];
  answerSchema: unknown;
  createdAt: string;
  expiresAt: string;
  state: 'draft'|'sent'|'answered'|'expired'|'cancelled';
  notificationChannel: 'telegram'|'whatsapp';
  notificationMessageId?: string;
};
```

Контракт ответа: `{clarificationId, ownerId, optionId|text, receivedAt, deliveryMessageId}`. Проверить подпись webhook/секрет, разрешённый `chat_id` + Telegram sender ID/номер владельца, наличие active record, option/schema, срок, уникальность id, версию состояния. Обновить state атомарно, затем возобновить **только** task/call по сохранённым foreign keys. Повторный callback — тот же результат, без повторного side effect.

Для свободного текста требовать **reply на конкретный message** или явный `#Q-918`; при нескольких открытых вопросах обычное сообщение без связи не направлять автоматически «в последний диалог».

## 4. Поведение во время активного звонка

```text
CONNECTED
  -> собеседник спрашивает то, чего агент не знает
  -> классификация: можно уточнить у контакта? если да, спросить его
  -> иначе freeze pending decision; создать ClarificationRequest
  -> отправить владельцу Telegram push с кнопками / reply
  -> голосом: «Позвольте, пожалуйста, я уточню один момент»
  -> короткое ограниченное ожидание (порог конфигурируется; начать с 15–20 сек)
     -> пришёл корректный ответ: продолжить разговор и отметить decision
     -> не пришёл: «Могу я уточнить и вернуться сообщением/перезвонить?»
  -> сохранить follow-up и завершить/продолжить без обещания результата
```

**Не держать 2 минуты молчания** и не класть собеседника на hold, если платформа не поддерживает настоящую удерживающую паузу. Можно продолжить собирать **другие независимые факты**, пока ответ ожидается. Ответ, полученный после завершения звонка, применяется к следующему текстовому ответу/обратному звонку, но не к законченному разговору.

При невозможности отправить push: fallback (второй канал или inbox UI) и безопасное завершение; агент **не принимает решение за владельца**, если требовалось разрешение.

## 5. Уведомления: режимы

- **Info:** «получен ответ/звонок завершён» (может группироваться).
- **Clarify:** быстрый выбор/ответ; можно настроить тихий режим.
- **Approval:** высокорисковое действие; дедлайн, точные последствия, сумма/валюта, получатель, одноразовое подтверждение. Не истолковывать «ок» как согласие на несколько независимых платежей.
- **Emergency:** потеря контроля над звонком/провайдером, достигнут бюджет, подозрительное действие; немедленно остановить без ожидания ответа.

Предпочтения: Telegram primary, WhatsApp fallback, web inbox always; возможно отключить push для info. WhatsApp owner identity должен быть отдельно от внешнего WhatsApp agent identity, чтобы не получить цикл ответов.

## 6. Негативные тесты приёмки

1. Два звонка одновременно → два вопроса; ответ к Q-1 не влияет на call-2.
2. Пользователь ответил через 1 минуту после `expiresAt` → ответ отмечен late, не применяется к уже завершённому звонку.
3. Неизвестный chat_id, подменённое callback_data → игнор/аудит.
4. Дважды нажата кнопка → обработка один раз.
5. Telegram webhook пришёл после рестарта API → workflow возобновляется по DB.
6. Owner делает `/stop` во время звонка → отмена всех связанных pending questions, попытка hangup и переход задачи в CANCELLED.
7. Неподходящий свободный ответ → запрос переформулировать, не отправлять внешнему адресату.
8. Нет интернета у Telegram → звонок не зависает и не подтверждает платные действия.
9. Owner отвечает на high-risk approval, истёкший/переведённый в другой статус → старый ответ не разрешает новое действие.
10. Утечка контента в Telegram запрещена настройками → в уведомлении только безопасное summary.

## 7. UX и observability

Dashboard показывает «ожидается владелец» + кто/какой контакт + deadline + кнопка отменить. Журнал хранит кто ответил, какое решение принято, был ли звонок ещё активен и как применён ответ. Метрики: время owner response, доля ответов до окончания звонка, сколько решений отложено, ложных маршрутизаций должно быть **0**.
